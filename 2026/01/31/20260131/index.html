Cronicle 備份搬移：從故障主機還原排程系統

發表於 2026-01-31 分類於 Learn ， DevOps Disqus： 文章字數： 2.8k 所需閱讀時間 ≈ 7 分鐘

記錄 Cronicle 排程系統的緊急搬移過程。A 地的 Linux VM 發生硬碟故障，檔案系統變成唯讀狀態無法寫入。趁著還能讀取資料，透過 scp 把 Cronicle 的 data 和 conf 拉到 B 地，用 Docker 重新建起來。

背景

A 地 Cronicle Server 因硬碟 I/O error 被系統強制 remount 成唯讀，導致 Cronicle 無法寫入 log 而啟動失敗。

系統日誌

使用 dmesg 查看核心訊息，確認硬碟發生 I/O 錯誤：

輸出：

從日誌可以看到：

  • I/O error：硬碟多個 sector 發生讀寫錯誤
  • JBD2 journal aborted：檔案系統日誌損壞
  • Remounting filesystem read-only：系統自動將檔案系統切換為唯讀模式保護資料

處理流程

  1. 搶救資料：趁還能讀取，scp 把 Cronicle 的 data/ 和 conf/ 備份拉到 B 地
  2. B 地建立備援：用 Docker 在 B 地把 Cronicle 跑起來
  3. 在 AI 的協助下，修復 A 地硬碟：執行 fsck -y 進行磁碟修復，再 reboot 恢復正常

結論

為什麼要備份到異地再修復？
fsck 修復有可能失敗，可能會有不可逆的狀況：

  • 修復過程中硬碟徹底損壞
  • fsck 自動刪除無法修復的檔案
  • 底層儲存問題未解決，修復後又再次出錯

因此先 scp 把資料拉到 B 地，確認服務能跑，再執行修復動作。即使 A 地整個掛掉，B 地還能撐住。
