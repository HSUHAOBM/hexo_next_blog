LINE Webhook Verify 失敗：An SSL connection error occurred

發表於 2026-06-17 分類於 Learn ， Web Disqus： 文章字數： 4.1k 所需閱讀時間 ≈ 10 分鐘

這次遇到 LINE Webhook Verify 失敗，後台只顯示 An SSL connection error occurred。

一開始線索指向 TLS Cipher Suite，抓封包後才收斂到憑證鏈相容性。

問題背景

在 LINE Developers 後台 Webhook settings 按下 Verify，跳出：

這不是正式 webhook event 處理失敗，而是 LINE 後台的 Verify 連線測試失敗。

環境如下：

  • Server：Windows Server 2019 / IIS
  • Domain：內部 API 子網域
  • 原本使用的憑證：公司網域的 wildcard certificate

一開始排查時，還不知道公司前陣子有更換 SSL 憑證。這是後來抓封包，看到 LINE 在收到 Server Certificate 後中止 TLS，才回頭確認出來的。

第一步：IIS Access Log 沒有 Request

LINE Developers 後台按下 Verify 後，IIS W3SVC log 沒有那筆 request。

request 沒進 IIS，先排除應用程式 routing、controller、HTTP status code 這類問題。

另外，我也用自己外網的 Linode 直接打同一支 webhook，HTTP request 可以正常進來。

這讓當時的判斷更偏向「LINE 到公司環境之間的連線問題」，而不是 webhook 程式或 URL 本身壞掉。

第二步：異地起服務，確認 LINE 來源 IP

接著我在另一個外部環境另外架了一個測試 webhook endpoint，
先讓 LINE Verify 打到那邊，確認 LINE 實際連線來源 IP。

請負責網路與防火牆的同事協助確認：

  • LINE IP 有沒有被防火牆擋掉
  • 伺服器 443 是否有收到連線
  • 中間網路設備有沒有 drop 或 reset

由於防火牆不是我管理，這段花很多時間在協調。每次只能先縮小可疑範圍，再請對應的人查。

防火牆沒有明顯阻擋後，往 Windows Server 本機 log 查。

第三步：檢查 HTTPERR Log

檢查：

HTTPERR 看到 LINE 來源 IP，結果是 ClientCancel。

LINE 有連到伺服器，但 request 沒進 IIS。問題位置往 HTTP.sys、Schannel、TLS handshake 收斂。

第四步：Windows Event Viewer 的 Schannel 錯誤

Windows 事件檢視器看到 Schannel 錯誤：

這個訊息讓我先往 TLS Cipher Suite 查。

第五步：用 IIS Crypto 檢查密碼套件

用 IIS Crypto 檢查 Windows Server 2019 的 TLS 設定，確認是否支援 ECDHE_RSA AES-GCM：

調整後，LINE Verify 仍然失敗。

額外踩雷：IIS Crypto 修改後導致連線異常

在 IIS Crypto 更新設定重開過好幾次，都沒有異常。
但某次 IIS Crypto 更新設定後再重開機，整台機器網路都連不上，也無法遠端進去。
只能再找負責伺服器的人，不透過遠端的方式，進去該伺服器，請他再打開 IIS Crypto，也只會跳錯誤。當下幾乎準備還原。

最後有想從群組原則救回來：

把「SSL 密碼套件順序」設成「已啟用」後，優先權會大於 IIS Crypto 的修改。啟用後覆蓋原本設定，網路恢復正常。之後就不再往密碼套件的方向查找。

到這裡，線索變成：

  • LINE 來源 IP 只出現在 HTTPERR
  • LINE 的 request 沒有出現在 IIS W3SVC log
  • Windows Event Viewer 指向 Schannel / TLS
  • IIS Crypto 調整 Cipher 後仍然沒有解決

LINE 的連線還沒進到 IIS Worker Process，問題位置可能在：

  • HTTP.sys
  • Schannel
  • TLS handshake
  • 憑證驗證
  • 更前面的連線協商階段

LINE 來源 IP 有連到伺服器 443。

ClientHello 內容：

  • SNI：內部 API 子網域
  • TLS 1.2 / TLS 1.3 支援
  • ALPN：h2 / http/1.1
  • ECDHE_RSA AES-GCM 類型的 Cipher Suites

ServerHello 成功選到：

這代表 TLS version、Cipher Suite、SNI、ALPN 都不是主要問題。

LINE 在收到 Server Certificate 之後，就中止了 TLS 連線，沒有繼續完成 handshake，也沒有送出 HTTP POST。

HTTP request 沒送出，IIS access log 自然不會有紀錄。

到這一步，我才回頭確認公司前陣子確實有更換過 SSL 憑證，問題才和憑證鏈串起來。

真正可疑的地方：憑證鏈

原本的憑證鏈是：

瀏覽器打得開，外部測試工具看起來也正常，但 LINE Webhook client 沒完成 TLS handshake。

這次封包看到的現象是：

  1. LINE ClientHello 正常。
  2. ServerHello 正常。
  3. Cipher、TLS version、ALPN 都選成功。
  4. Server Certificate 送出後，LINE 中止 TLS。
  5. LINE 沒有送 HTTP POST。

當時比較合理的懷疑是：LINE Webhook client 對原本那條憑證鏈，可能存在 trust store 或 path building 相容性問題。

這裡不能直接寫成「LINE 不信任某家 CA」。比較精準的說法是：這台 server、這個 binding、這張憑證鏈的組合下，LINE Webhook client 沒有完成 TLS handshake。

A/B 測試：只把 API 子網域換成 Let’s Encrypt

為了確認是不是憑證問題，又不影響其他服務，只調整內部 API 子網域的 IIS binding。

用 win-acme 申請 Let’s Encrypt 憑證，只套用在 Webhook 對應的 IIS 站台。

IIS Binding 改成 Let’s Encrypt 後，LINE Webhook Verify 立即恢復正常。

到這一步就能確認，問題不是 Webhook 程式、IIS routing、TLS Cipher 或防火牆，而是原本那張憑證或憑證鏈在 LINE Webhook client 上的相容性問題。

結論

這次最容易誤判的地方，是外部測試其實會通。

我用 Linode 從外網打 webhook 可以進 IIS，瀏覽器和一般測試工具看起來也正常。再加上 Windows Event Viewer 的 Schannel 錯誤指向 Cipher Suite，所以一開始根本不會想到是 SSL 憑證鏈。

真正把方向拉回來的是封包：

  • LINE 有連到 443
  • ClientHello 有帶 SNI
  • ServerHello 成功選到 TLS 1.2、ECDHE_RSA AES-GCM、h2
  • LINE 收到 Server Certificate 後中止 TLS
  • HTTP POST 沒送出，所以 IIS access log 沒紀錄

我不能直接下結論說某家 CA 一定有問題。比較精準的說法是：原本那條憑證鏈在瀏覽器和一般外部測試都正常，但 LINE Webhook Verify 沒有完成 TLS handshake；只把 webhook 對應站台改成 Let’s Encrypt 後，LINE Verify 立即恢復，因此可以確認問題就在原憑證或憑證鏈相容性。

所以這次的經驗是：Webhook client 的 TLS 行為不一定跟瀏覽器或一般 curl 測試一致。當 IIS 沒 log、HTTPERR 有 ClientCancel、Schannel 又只給模糊錯誤時，最後還是要靠封包確認連線到底停在哪一段。
